## Threat model

Foxhound recovers failed Stripe payments, handles disputes, and bills the merchant for that work. The Worker `foxhound` is the public app at `foxhoundapp.com` and `www.foxhoundapp.com`. A second Worker, `foxhound-admin-mcp`, is declared for `admin-mcp.foxhoundapp.com`. It has a service binding to `foxhound` and an OAuth KV. It has no Stripe key and no D1. Live DNS does not resolve that hostname. CI deploys the main Worker only.

Callers:

- Anonymous visitors on marketing pages, the audit estimator, and `GET /health`.
- A merchant signed in with Better Auth (email or Google), scoped to an account membership.
- A demo cookie, which may look around and may not mutate.
- Stripe, on two webhook URLs, after signature verification with two different secrets.
- Cron (`*/5`, nightly, monthly) and three queues.
- A merchant MCP bearer key on `POST /mcp`.
- An admin, through Cloudflare Access on `/admin`, or through an admin MCP key plus an email header on `/api/admin/v1`.

Trust changes at: Stripe signature verification, the app-shell membership check, Access JWT plus `ADMIN_EMAIL`, the two MCP authenticators, Turnstile on the audit action, and the encryption boundary around Stripe Connect tokens. Google OAuth tokens sit on the wrong side of that last boundary (FH-5).

STRIDE, short: spoofing is the webhook signature and the session; tampering is a money batch or a billing status; repudiation is the webhook payload and the admin audit log; information disclosure is customer payment data, evidence files, and tokens at rest; denial of service is the public routes and the MCP body parser (FH-4); elevation is a membership or an admin key used outside Access (FH-20).

## Findings

### FH-1 MAJOR, area 4 and 5, confidence confirmed

`claimUnknownAccount` (`app/lib/webhooks/process.ts` lines 93-108) inserts the full Stripe event and then `catch { }` with a comment that the unique index makes a replay a no-op. The catch does not test `isUniqueConstraintError`. `processConnectedWebhook` (lines 47-51) then returns `{ status: "ignored" }`. The route (`app/routes/webhooks/stripe.ts` lines 45-52) returns 200 for every outcome other than `error`. Stripe stops.

`claimUnroutableEvent` (`app/lib/billing/platform-webhook.ts` lines 154-173) is the same shape and returns false on every throw. The caller (lines 120-125) treats false as `{ status: "duplicate" }`. The platform route then answers 200.

A transient D1 failure, or a payload D1 refuses, is recorded as handled. The event is not retried. The normal platform billing path does not depend on this helper: `resolvePlatformBillingTarget` throws on a select failure, and a mapped invoice with a local row goes through `executeMoneyWrite`. The helper runs when the event maps to no local `billing_invoices` row.

Smallest fix: rethrow unless `isUniqueConstraintError`. The route already turns a thrown error into a 500, which is what Stripe retries.

### FH-4 MAJOR, area 2 and 12, confidence confirmed

`@modelcontextprotocol/server` 2.0.0 is the installed version. `npm audit` lists three highs on `>=2.0.0 <2.3.0`: a shared transport can deliver one HTTP client's messages to another; one request inside the default size limit can exhaust memory during validation; server bearer authentication can accept a token issued for another service. `maxToolInputElements` does not appear in this install's `@modelcontextprotocol` type declarations.

Both doors authenticate before the SDK sees the body. The merchant door checks the bearer key, then calls `serveMcp` (`app/lib/mcp/server.ts` lines 106-111), which builds `createMcpHandler(() => buildMcpServer(...))` per request. The admin door is behind `workers-oauth-provider`, then `guardMcpRequest`, then a per-request factory in `mcp/src/server.ts`. A per-request factory is the shape the shared-transport advisory treats as unaffected. These doors do not use the SDK's bearer authenticator. The memory title remains: an authenticated caller can send a body the SDK validates with no element cap.

An anonymous caller does not reach the SDK. The caller already holds a key. Live `GET` of the webhook URLs is a separate bug (FH-15). `GET /mcp` was not re-fetched this pass beyond the admin host, which does not resolve (FH-16).

Smallest fix: upgrade `@modelcontextprotocol/server` to `>=2.3.0` and set the element cap if that version exposes it.
